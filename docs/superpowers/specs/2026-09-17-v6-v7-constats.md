## V7-1 — Prime Gaming — **ENTRÉE FERMÉE**

### Ce qui a été mesuré

```
gaming.amazon.com   HTTP 200 — 10 631 octets, titre « Amazon Luna Cloud Gaming », 514 ms
Cartes d'offre      0
Liens luna.amazon   0
Mention « Prime Gaming » dans le texte : absente
Données embarquées  0 bloc
```

### Ce qu'on en conclut

Le commentaire de `src/core/25-luna-entry.js:28` disait vrai. Le domaine répond,
mais **ce qu'il sert est l'application Luna** : c'est le titre de la page qui le
dit, et l'absence complète du mot « Prime Gaming » le confirme.

Dix kilo-octets, c'est une coquille : la page est rendue côté client. Prise
seule, l'absence de cartes d'offre ne prouverait donc rien — une application
JavaScript vide sa page de tout contenu statique. Mais deux autres faits
lèvent l'ambiguïté :

- le **titre** est servi par le HTML, et il annonce Luna, pas Prime Gaming ;
- il n'y a **aucun bloc de données embarquées**, donc aucun catalogue caché
  dans la page qu'un adaptateur pourrait lire.

Et surtout, il n'y a rien à gagner : les réclamations Prime vivent déjà sous
`luna.amazon.*/claims`, que l'extension couvre depuis le début.

### Ce que la mesure ne dit pas

Elle est **anonyme**. Un compte connecté verrait peut-être une autre
application. Cela ne change pas la conclusion : même dans ce cas, le contenu
serait chargé en JavaScript après authentification, hors de portée d'une
source de découverte, et la réclamation resterait sur le domaine Luna.

**Décision : l'entrée sort de la feuille de route.** Le module Luna couvre déjà
le seul endroit où les offres se réclament.

## V6-1 — Une source GOG en propre — **MESURE À AFFINER**

### Ce qui a été mesuré

```
gog.com             HTTP 200 — 953 771 octets, titre « Bienvenue sur GOG.com », 612 ms
.giveaway__title    0
#giveaway           0
[class*="giveaway"] 0
a[href*="/game/"]   24
Mot « giveaway » dans le texte : oui        <-- AMBIGU, voir plus bas
Données embarquées  3 blocs
```

### Trois bonnes nouvelles

1. **La page est rendue côté serveur.** 953 Ko, et vingt-quatre liens produit
   présents dès le HTML brut : contrairement à `store.epicgames.com` (mesuré en
   V0-3, entièrement rendu côté client), GOG peut être lu par une source HTML.
   C'est exactement ce que le document offscreen sait faire.
2. **Il y a trois blocs de données embarquées.** Sur une page rendue côté
   serveur, c'est souvent là que vit l'état complet — plus fiable qu'un
   sélecteur de classe, qui change à chaque refonte du CSS.
3. **Le reste de la chaîne est prêt** : `watch/offscreen.js` lit, la source n'a
   plus qu'à transformer.

### L'ambiguïté, et pourquoi elle est de notre faute

Le « oui » du mot « giveaway » ne veut rien dire en l'état : la sonde le
cherchait dans `document.body.textContent`, **qui inclut le contenu des balises
`<script>`**. Ce « oui » peut donc signifier deux choses opposées :

- la page **affiche** un giveaway → un sélecteur de rendu suffit ;
- le mot voyage seulement dans du **JSON embarqué** → il faut lire ce JSON.

Les deux n'appellent pas le même code. La sonde mesure désormais les deux
séparément (texte rendu sans les scripts, et source brute), et regarde à
l'intérieur de chaque bloc embarqué lequel porte le mot.

### L'autre lecture possible, et il faut la garder en tête

Zéro élément portant une classe `giveaway` ne prouve pas que le sélecteur a
changé. Cela peut simplement vouloir dire qu'**aucun giveaway ne tournait au
moment de la mesure** — c'est même l'explication la plus économique. Un
giveaway GOG dure quelques jours ; la page d'accueil n'affiche rien entre deux.

C'est pourquoi la mesure suivante doit rapporter la STRUCTURE et pas seulement
des comptes : savoir quel bloc embarqué existe, et ce qu'il contient, permet
d'écrire une source qui trouvera le giveaway le jour où il y en aura un — au
lieu d'attendre qu'il y en ait un pour pouvoir écrire la source.

**Décision : l'entrée reste, avec une mesure de plus à prendre** — la même
section, relancée après mise à jour de l'extension.
